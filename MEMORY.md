# MEMORY.md

Non-obvious findings about this codebase and its operating environment, discovered during work but not designed for anywhere else — not in README.md (what it is and how to use it), DESIGN.md (architectural decisions), or agent-instruction files (rules). This is background context for whichever LLM works in this repository next, so it does not have to rediscover these findings the hard way.

If you (an LLM) make a finding like the ones below — a gotcha, an environment quirk, or a non-obvious reason one component reads or uses another — add it here rather than only mentioning it in chat. Keep entries factual and dated; note when something might have been fixed since.

## Findings

- 2026-06-10 — With `MAX_TOKENS = 4096`, Anthropic domain-agent calls truncated mid-response on the full structured JSON output, producing JSON parse errors rather than a clean failure. Raised to 8192 (commit 760902e). If parse errors reappear (e.g. after adding fields to an agent's output schema), check `MAX_TOKENS` in `agents/backends.py` before assuming a prompt or provider problem — the failure mode looks like a parsing bug, not a token-limit bug.

- 2026-09-25 — The Ollama default is `gemma4:26b`. A live `--agents hmda` batch against `sample_loan.json` completed with parsed HMDA and automatic auditor results (no parse errors) using that default. On the local 31 GiB RAM / 8 GiB VRAM WSL machine with a 65,536-token Ollama context, the two sequential calls took 6m24s total; a full seven-agent batch should be treated as a long-running, adequately provisioned-machine test.
- 2026-10-08 — `mcp` 2.x renamed FastMCP to `mcp.server.mcpserver.MCPServer` (`from mcp.server.fastmcp import ...` raises a migration error); the in-process `Client(server_obj)` makes MCP tools testable without a subprocess. The `a2a-sdk` 1.x `DefaultRequestHandlerV2` rejects a `TaskStatusUpdateEvent` unless the executor first enqueues a `Task` (`new_task_from_user_message`); the symptom is a JSON-RPC "Agent should enqueue Task before TaskStatusUpdateEvent" error. The SDK also logs a harmless "EventQueueSource ... cancelled" warning when `asyncio.run` exits.
- 2026-10-08 — Local `gemma4:26b` does not reliably call the MCP tool (it did in one live run, skipped it in the next). That is why `agents/runner.py` has a harness fallback that calls the tool and injects the result; a `tool_calls[].by == "harness"` entry is expected behavior, not a bug. The harness also overwrites the model's tool arguments with the loan payload's canonical case (logged at WARNING when they differ).
- 2026-10-08 — Ollama silently truncates input beyond its context window. The builder agents send ~25-100 KB prompts; set `OLLAMA_NUM_CTX` (honored in `agents/backends.py`) or use a remote model, otherwise a truncated prompt produces plausible-looking but wrong builder output.
- 2026-10-08 — eCFR's versioner API needs `Accept-Encoding` compression and a date no later than the title's `up_to_date_as_of` (from `/api/versioner/v1/titles.json`), otherwise it returns 406/404. FFIEC (APOR tables), FEMA and some FCA pages return 403/404 to scripts; the source registry marks those `manual`.
- 2026-10-09 — First full local run (gemma4:26b, `concurrency: 1`, all 8 domain agents + auditor + narrative): ~17.5 min of model time, every call parsed, max prompt 17.5k of 32k tokens. Tool-backed agents called their MCP tool themselves 3/3 in the full run (2/3 in the earlier 3-agent run; the harness fallback covered the miss, costing one wasted ~110 s call). The ungrounded-statement guard (`compliance_common/assemble.py: grounding`) caught real model errors: evidence listed as present that is not in the input, a mistyped case id (TEST-2004-001), and a garbled token (`Apprimary_evidence_present`). Prompts without the "Terminology" and "Evidence and identifiers" rules produced a wrong APOR expansion.
- 2026-10-09 — If the machine sleeps mid-run, WSL's clock jumps but process timeouts use monotonic time, so an in-flight Ollama call just resumes and finishes after wake (observed: 2 h wall gap, HPML call completed). Keep the machine awake for long runs anyway.
- 2026-10-09 — CORRECTION to an earlier note: the un-ported HMDA/ECOA agents (gemma) said missing marital status was a "failure to collect mandatory demographic data". I first judged that wrong; it is substantially RIGHT. 12 CFR 1002.13(a)(1) (Reg B) requires the creditor to *request* ethnicity, race, sex, marital status (married/unmarried/separated) and age for an application primarily to purchase or refinance a 1-4 unit dwelling that is the applicant's principal residence and secures the loan; the applicant may decline, and the declination must be noted on the form (1002.13(b)). What gemma got wrong was attributing it to HMDA, whose data (12 CFR 1003.4(a)(10)) has no marital status field. Lesson: verify against the pinned regulation text before calling a model wrong. Also: `hmda_fields.rate_spread` should be derived from the same APOR as HPML, not supplied (the sample's 2.37 vs the true 1.26 was caught by the auditor).
- 2026-10-09 — Local model sizing on this machine (RTX 5070 Laptop, 8 GB; Ollama is a systemd service inside WSL, not on Windows: `systemctl status ollama`): only ~6.1 GB of the 8 GB is usable by Ollama. granite4.1:8b (5.3 GB on disk) never fits fully on the GPU, even at an 8k context (6.84 GB needed; ~0.7 GB spills to CPU; at 24k, 3.6 GB spills) and then runs CPU-bound at ~13-20 tok/s. granite4.1:3b (2.1 GB) stays fully on the GPU up to a 32k context (4.98 GB) and runs at ~50-80 tok/s; at 49k it spills. Set `OLLAMA_NUM_CTX` explicitly: it decides whether a model fits.
- 2026-10-09 — Granite 3B vs Gemma 26B on the full sample pipeline (all deterministic classifications identical, because code decides): the 3B ran the eight evaluator-backed agents in 12-19 s each (~4 min whole pipeline, vs ~17.5 min for Gemma). The 3B never called the MCP tool itself (8/8 by the harness, so its first call is wasted work); Gemma did (3/3 in the full run). The 3B's per-agent narratives were good and the grounding guard caught its fabrications (e.g. "HMDA case summary" listed as evidence), but its cross-agent synthesis was weak: the auditor reported no systemic issues and missed the HPML/HMDA rate-spread conflict, and its report mislabeled a Potentially Covered HMDA result as Not Applicable. Use a stronger model for the auditor and narrative agents (see ~/.config/compliance_poc/agents.mixed.yaml), or make the cross-agent checks deterministic.
- 2026-10-09 — CORRECTION: Ollama runs as a systemd service inside WSL (`/etc/systemd/system/ollama.service`, drop-in `ollama.service.d/override.conf` sets OLLAMA_NO_CLOUD=1 and OLLAMA_CONTEXT_LENGTH=65536 — that 65k default is why unconfigured models load with a big context). Changing the service needs sudo, which needs a password the agent does not have; ask the user to apply it. Restarting it kills any benchmark or batch in flight.
- 2026-10-09 — Tool calling by small local models: with the "tool in hand" prompt and forced-first-call logic, no model under ~9B reliably called its MCP tool itself (lfm2.5:8b, granite4.1:3b, gemma4:e4b, ministral-3:3b: harness fallback every time; qwen3.5:4b sometimes). Ministral's malformed tool call made Ollama return HTTP 500 and crashed an agent run before the runner learned to fall back. Default small local models to `tool_mode: seeded` in agents.yaml (the harness makes the call and puts it in the conversation as the agent's own first step; one model call instead of two).
- 2026-10-09 — Thinking: thinking-capable Ollama models (gemma4, qwen3.5, lfm2.5) emit hidden reasoning tokens that multiply latency (gemma4:26b made ~2,300 output tokens before a short tool call). `agents/backends.py` now sends `think: false` for models that advertise the capability unless OLLAMA_THINK=true; thinking is logged at TRACE when on. Earlier Gemma timings in these notes were measured with thinking ON.
- 2026-10-09 — Model choice (details and tables in benchmarks/RESULTS.md): granite4.1:3b for the eight domain agents, qwen3.5:4b for the auditor narrative and final report, `tool_mode: seeded`, `OLLAMA_NUM_THREAD=4`, constrained output via NARRATIVE_SCHEMA. Whole sample pipeline ~3 min (vs ~17.5 min on gemma4:26b). Accuracy differences among qwen/granite/gemma-e4b are inside the noise (SE ~4-5 points); speed and footprint decide. Small models still make false statements (granite called a Non-Compliant VMI result compliant; invented evidence); the guards catch and flag them and the code-owned decision is never affected.
- 2026-10-09 — Gotchas found while benchmarking: (1) `ollama run <model> "prompt"` waits forever on stdin when stdin is not a terminal; add `< /dev/null`. (2) Lfm2.5 puts `<think>...</think>` inline in the content; `agents/runner.py` strips it (and logs it at TRACE) before parsing JSON. (3) Even with a fixed seed, GPU runs are not bit-identical (same cell scored 70 and 85). (4) A scorer must score an empty answer as 0, or failures look like 50%. (5) ministral-3's malformed tool call makes Ollama return HTTP 500; the runner falls back to the harness.
- 2026-10-09 — pancode-coder (qwen2.5-coder:7b-instruct-q4_K_M, num_ctx 32768, num_predict 4096) baseline under the CURRENT Ollama settings (f16 KV cache): 6.8 GB loaded, 12%/88% CPU/GPU split, 43.8 tok/s generation, 623 tok/s prompt eval, 8.7 s load. The planned OLLAMA_FLASH_ATTENTION=1 / OLLAMA_KV_CACHE_TYPE=q8_0 / NUM_PARALLEL=1 / MAX_LOADED_MODELS=1 override needs sudo to apply and affects every model; re-measure fit after applying it.
- 2026-10-09 — Narrate-only tightening. Diagnosis: the earlier "VMI contradiction" was a regex false positive on a sloppy sentence, and most "invented evidence" was real data from other loan sections (only the FZD "included in HMDA case" item was truly fabricated). Fixes: the model sees only its own case; it writes three prose fields only; evidence/data-quality/change blocks and scope notes are code-owned; narratives are fact-checked, retried once, then replaced by a code-written narrative. Granite 3B seeded, 8 agents x seeds 42/7: heuristic accuracy 92.5 / 88.8 (was ~84), 2 of 8 narratives fell back to the deterministic text on seed 42 and 1 of 8 on seed 7 (contradiction watchdog; since narrowed to Compliant results only because "fails to exceed the spread" is normal on Not Applicable).
- 2026-10-12 — The Ollama service override now has `OLLAMA_FLASH_ATTENTION=1`, `OLLAMA_KV_CACHE_TYPE=q8_0`, `OLLAMA_NUM_PARALLEL=1`, and `OLLAMA_MAX_LOADED_MODELS=1`; verified loaded in systemd during the non-Gemma comparison. With context 32768, `OLLAMA_NUM_THREAD=4`, temperature 0.2, and seeds 42/7, `granite4.1:3b`, `qwen3.5:4b`, `lfm2.5:8b`, and `ministral-3:3b` were benchmarked once on each of eight domains per seed and once each through the full sample pipeline. Results and caveats are in `benchmarks/RESULTS.md`. Core evaluator and auditor decisions were identical across models. The narrative heuristic favored Qwen (96.2 mean) by a small margin over Granite (95.3), but this is one loan/two seeds; Granite was faster (6.2 vs 9.5 s/cell) and used less GPU memory (3.63 vs 4.25 GB peak). LFM2.5 was quickest per cell (3.2 s) but had a guarded TRID failure in the full run and exported a report containing `<think>` and instruction-like prompt text. Review complete reports, not only scores or structured parse status. The four Ollama service settings were held constant, not A/B-tested; do not infer their performance effect from this comparison.

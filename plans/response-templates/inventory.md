# Failure inventory by regime

Derived 2026-11-07 from `compliance_mcp/*/rules.py`, `compliance_mcp/hmda/lar.py` and `compliance_common/{decision,assemble,narrative}.py`. Re-derive from the code rather than trusting this list. Authoritative sources are the pinned eCFR snapshots in each `compliance_mcp/<domain>/pack/sources/` and the registry in `builders/sources.yaml`. Citations below are the ones the evaluators already emit.

## How a finding is made

- A rule result has an `outcome`: `satisfied`, `not_satisfied`, `unable_to_determine`, `review_required`, `applies`, `does_not_apply`, `eligible`, `not_eligible`. A **finding** is a result that is `not_satisfied`, `unable_to_determine` or `review_required` (`_BAD` in `compliance_common/narrative.py`). `not_eligible` is a normal YBS outcome, not a defect.
- Each failing rule has a cause of one kind. This inventory uses four kinds, because the reader and the action differ:
  - **G, information gap.** A fact is absent or in conflict (`missing_facts` entry). The evaluator never guesses. The action is to obtain or record the fact.
  - **V, value or timing violation.** The facts are present and break the rule (late notice, wrong value, amount below the required level).
  - **R, reviewer judgment.** The rule needs a human decision (`review_required`).
  - **P, process or record fact.** The fact is about what the institution did (was marital status asked, was a disclosure given). It is **not** a request to the customer.
- Result mapping: any `not_satisfied` gives `Non-Compliant` (YBS excepted); any `unable_to_determine` or `review_required` gives `Potential Issue`; scope failures give `Not Applicable`.

## What the two templates need from this

1. **Dynamic rule ids.** `HMDA-LAR-{nn}`, `HMDA-EXCL-{KEY}`, `VMI-REQUEST-{ITEM}`, `VMI-OBSERVATION-{ITEM}`, `YBS-ENTITY-{CATEGORY}-{SUFFIX}` and `YBS-PERSON-{CATEGORY}-PRODUCER` are built at run time. A catalog keyed by literal id is not enough. It needs patterns, and a test must prove every id the code can emit has an entry.
2. **Missing-fact field names are not customer words.** Examples: `lar_context.income_considered`, `monitoring.items.race.declination_noted`, `notice.contents.ecoa_notice`. The loan-officer template needs a label for each field and must hide internal paths.
3. **Not every gap is a customer request.** `ECOA-MARITAL-INQUIRY` records whether the institution asked about marital status. Telling a loan officer to "obtain marital status" could cause the violation the rule tests (1002.5(d)(1)). The same holds for `ECOA-SPOUSE-SIGNATURE`, `ECOA-AGE-PUBLIC-ASSISTANCE`, TRID delivery records and all `lar_context.*` flags. Kind P and R findings must be routed away from the customer list.
4. **Demographic items the applicant may decline.** For VMI and HMDA items 10, the loan officer asks, the applicant may decline, and the decline is recorded. The template must say so.
5. **Values the narrative may quote.** Only numbers, dates and ids in the decision record, the case or the pinned regulation text. `check_narrative` already enforces this and must keep doing so for template paragraphs.
